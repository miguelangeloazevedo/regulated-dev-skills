# Worked example: a parser dependency update

Fictional planning exercise. No package has been upgraded, rebuilt or released.

A supported parser changes from one exact evaluated version to another. Before editing, record the permitted plan class or approved CR; do not call it a harmless dependency bump. `soup-from-code` identifies the incorporated component; `security-diligence` assesses advisories, and the SOUP owner compares functional/host requirements and anomaly lists.

The baseline manifest would identify source commit, parser artifact/version, lockfile, build scripts, compiler/runtime, supported configuration, test fixtures and produced artifact. A real hash is calculated only from the actual artifact. No hash is supplied here because nothing was built.

Planned verification includes existing parse requirements, changed edge cases and affected safety controls. The clean rebuild and interrupted-update/recovery exercise run only in an isolated non-production target with synthetic messages. Results, logs and acceptance are **open**, not implied by the proposed manifest.

If generated output differs, determine whether the plan requires byte equality or equivalent identified behaviour, and investigate undeclared inputs. The change owner and QA/RA review the delta and required evidence. `package` reconciles the tested manifest with the export; `/release` is still a human decision after the real evidence exists.
